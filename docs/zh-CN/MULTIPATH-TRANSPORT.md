# 多路径传输容灾、弱网调优与端到端测量方法论

> [!IMPORTANT]
> **合规使用前提**：本文档探讨广域网（WAN）跨区域高时延、高丢包及运营商级 NAT（CGNAT）环境下的传输层工程实践，仅适用于合法授权的边缘网关运维与网络协议研究。部署前请务必阅读 [法律合规与免责声明](../../DISCLAIMER.md)。

> 本文档回答一个核心系统工程问题：**为什么一个“本机探活全绿”的边缘节点，在不同运营商网络、不同时段下会表现出截然不同的吞吐与握手成功率，以及如何通过不相关路径冗余将其构建成确定性可用的传输底座。**
>
> 每一条设计均对应一次真实线上故障或端到端受控测量。凡是“直觉上合理但被实测证伪”的假设，本文保留完整的证伪推演 —— 因为后续维护者最容易重踩的，正是那个看似合理的版本。

---

## 0. 一句话结论

**在异构广域网中，单一传输路径必然会在特定运营商 QoS、CGNAT 或非对称路由下退化甚至中断，且退化发生时服务端往往毫无报错。** 因此本栈默认同时暴露三条传输特性互补的路径，交由客户端 `urltest` 自动并发选路：

| 路径 | 传输层 | 核心适用场景 | 典型受限条件 |
|---|---|---|---|
| **REALITY** | TCP 443 + 备用口 | 常规固网宽带骨干直连，无中转跳数损耗 | 严格中间盒或移动 CGNAT 下偶发 TLS ClientHello 挂起或按端口限速 |
| **Hysteria2** | UDP / QUIC | TCP 拥塞回退严重、高丢包长肥管道（LFN） | 部分企业内网或蜂窝运营商策略性丢弃高带宽 UDP 流 |
| **CDN 中转** | TCP 443 → Anycast CDN → 源站 | **源站直连路由出现 BGP 黑洞、跨网丢包或严格防火墙隔离时的兜底通路** | 需自备域名与证书；增加一跳边缘转发时延 |

三条路径并非同质冗余，而是**故障模式正交互补** —— 它们的退化诱因互不重叠。

## 1. 协议选型：为什么默认不是 AnyReality

本仓库早期曾将 **AnyTLS + REALITY** 设为默认，服务端侧的工程论证完全成立：自定义长度填充可平滑嵌套 TLS 报文特征，REALITY 省去证书签发运维，弱网吞吐优于传统 TLS 隧道。**但将它作为默认值依然是错误的。**

错误不在传输层推理，而在于**选型时只评估了服务端能力，忽略了客户端内核生态的表达覆盖面**：

> mihomo 的 `anytls` 配置块**没有 `reality-opts` 字段**，`public-key` / `short-id` 无处挂载（[官方文档](https://wiki.metacubex.one/en/config/proxies/anytls/) · [issue #2155](https://github.com/MetaCubeX/mihomo/issues/2155)）。这导致在 Clash 系订阅产物中，**主力节点根本无法被序列化表达**。

这一故障的隐蔽性极具警示意义：

- 服务端状态全绿，`sing-box check` 校验通过；
- 使用 sing-box 内核的客户端完全正常，零异常反馈；
- **唯独 Clash / mihomo 客户端缺少主力节点，且界面表现为“列表里少了几个条目”，而非显式报错。**

由于服务端侧看不出任何异常，该静默退化极难从监控日志中发现。

> **选型铁律**：选定默认协议的第一个问题不是“谁更快”，而是**“目标覆盖的每一个主流客户端内核，都能完整无损地表达这个节点吗”**。仅单一内核可表达的协议，若设为默认，等于静默丢弃另一半客户端生态。

因此现行策略为：

- **默认 `--protocol vless-reality`**（VLESS + REALITY + `xtls-rprx-vision`）—— `sing-box` 与 `mihomo` 双生态完整支持；
- **`--protocol anytls-reality` 作为显式可选项保留**：帧填充能力更强，但启用后**不生成 Clash YAML 订阅**（安装器明确提示，`build_profile.py` 直接拒绝输出残缺 YAML）。

### 推论：架构演进后必须全仓清扫遗留脚本与文档

一份**自信地指向过期架构的文档，比没有文档更危险**。协议或配置结构变更后，必须同步检索所有未挂载在 systemd/cron 上的辅助脚本与文档描述，杜绝配置漂移。

## 2. 端口策略：443 为主口，多备用口动态竞速

在某条固网宽带链路上开展的第一轮基线测量曾得出看似确定的结论：

| 测试项 | 实测结果 |
|---|---|
| 裸 TCP 三次握手（22 / 80 / 443 / 2087） | ✅ 全部连通 |
| 高位端口 TLS 会话（2053 / 2083 / 2087） | ❌ 连续 440 次握手超时 |
| 标准端口 **443** TLS 会话 | ✅ 稳定连通（195–242 ms） |

当时的链路表现为中间盒放行 TCP SYN、但丢弃非标准端口上的后续握手载荷。若仅凭单次测量，很容易得出“高位端口无用，只留 443 即可”的静态结论。

**然而五周后在同一条物理链路上复测，排序完全反转：**

| 端口 | 端到端握手与首包延迟 |
|---|---|
| 443 | 1520–3783 ms（触发流控队列） |
| 8880 | **1269 ms** |
| 40443 | **1264 ms** |

标准端口 443 因承载汇聚流量触发运营商动态流控而变为最慢端口；同期另一移动蜂窝链路在 443 上出现 ClientHello 后挂起 12 秒的现象。

> **核心教训：单时间点、单运营商路径的端口测量结论具有保质期。** 广域网的流控策略与拥塞队列按运营商、按端口、按周动态演化。

因此现行端口架构为：**以 `443` 作为默认主监听口（企业防火墙与公共 Wi-Fi 通行率最高），同时默认通过内核态 NAT 将 `2096 / 8880 / 40443` 重定向至主口，由客户端 `urltest` 周期性择优。**

备用端口采用 **`iptables` / `ip6tables` `nat/PREROUTING` `REDIRECT`** 实现，而非在应用层重复绑定多个监听实例：

- `sing-box` 配置文件零膨胀，无需维护多份入站配置同步；
- 卸载与回退只需清理独立命名链 `ANYREALITY_ALTPORT`，绝不污染宿主机上其他服务（如容器网络）的 NAT 表；
- 由于目标端口改写发生在 `nat/PREROUTING`，进入 `filter/INPUT` 时目的端口已变为 `443`，**UFW 无需额外放行备用端口规则**；
- **运维须知**：备用端口**不会出现在 `ss -tlnp` 的用户态监听列表中**，这是内核态 PREROUTING 重定向的正常机制，切勿误判为故障。

```bash
# 核查内核态实际生效的重定向规则与命中包计数
iptables -t nat -S ANYREALITY_ALTPORT
```

## 3. 客户端冷启动死锁：消除“下载分流规则依赖尚未就绪的隧道”循环依赖

这是客户端侧影响面最广的工程陷阱，典型用户侧现象为**“客户端启动瞬间闪退，或开机后陷入无限重启循环”**。

### 死锁形成链路

1. `sing-box` 启动阶段要求同步拉取全部 `type: remote` 规则集，任一下载失败即触发 `FATAL: initialize rule-set` 并直接退出进程；
2. 规则集拉取若配置了 `download_detour` 指向自动选路组，在**冷启动首秒 `urltest` 尚未产生任何探测样本，只能盲选第 0 号成员**；
3. 在固网链路上若 0 号成员恰好可达，1 秒内拉取完毕，问题被掩盖；
4. 在弱网或受限链路上若 0 号成员不可达，5 秒连接超时后内核立即 `FATAL` 退出 → 客户端守护进程拉起内核 → 再次命中同一 0 号死节点，形成冷启动死锁。

“偶发重启电脑又能连上”仅仅是因为网络抖动窗口变化使某次初始拉取碰巧成功，隐患从未根除。

### 三道确定性防线

| 防线层级 | 本栈工程实现 |
|---|---|
| **订阅产物全内联** | 所有 `rule_set` 强制编译为 `type: inline`，**客户端冷启动期间零外部网络请求**。`check_profile.py` 严格拦截任何 `type: remote` 条目，校验未过禁止 `rebuild-profiles.sh` 发布 |
| **自动组冷启动排序** | `⚡ Auto` 组强制将**广域可达面最宽的路径（启用 CDN 时为 CDN 中转组）排在 0 号位**，确保冷启动首包落入高存活通道 |
| **服务端异步周更** | 规则集拉取与反编译全部上移至具备稳定上行带宽的服务器，由 `refresh-rulesets.timer` 每周原子刷新；拉取失败自动保留上一版完好快照 |

在实机环境下的体积开销实测表明，**选对上游编译源后，内联体积远小于预期**：

| 规则集 | 规则条目数 | JSON 原始体积 |
|---|---:|---:|
| `geosite-cn` | 9,131 | 152 KiB |
| `geoip-cn` | 7,876 | 142 KiB |
| `geosite-category-ads-all` | 890 | 18 KiB |
| `geosite-cn-extra`（本仓补充） | 71 | 1 KiB |

生成的完整客户端配置原始体积约 **0.56 MiB**，经订阅服务内置 `Accept-Encoding: gzip` 预压缩缓存后，**线上传输体积仅约 81–84 KiB** —— 不仅彻底消除了启动期 5 次并发外部请求（原合计约 280 KB），还大幅降低了弱网环境下的订阅同步耗时。

> ⚠️ **上游源选择陷阱**：部分第三方镜像将 `geosite` 属性变体全量摊平，同样覆盖面会膨胀至 **111,305 条 / 1.7 MiB**（整体订阅达 3.36 MiB）。因此 `fetch-rulesets.sh` 优先使用本地 `sing-box rule-set decompile` 反编译官方紧凑 `.srs` 二进制包，仅在极端缺失环境下回退至 JSON 镜像并输出告警。

```bash
# 客户端自查：若内核日志中仍出现外部规则集拉取，说明客户端残留了旧版或其他来源的远程订阅
grep -c "raw.githubusercontent" <客户端 kernel.log>
```

## 4. 分组编排：为什么 `⚡ Auto` 默认不混入直连 REALITY

`urltest` 在冷启动首包尚无测速数据时固定选用第 0 号成员。当启用多路径时，默认编排顺序为 **`☁️ CF Relay` → `📡 Hysteria2`**，而将 `🚀 REALITY` 保留在手动选择器 `🎯 Select` 中一键可达。原因有二：

**① 避免长挂起探测阻塞自动组周期。** 在部分严格 NAT 或中间盒对特定 TCP 握手实施 7–12 秒静默丢包的链路上，将该成员混入自动组会导致每个探测周期都有工作协程长期阻塞在超时等待上。

**② 在跨洋长肥管道（220 ms RTT）多轮交叉轮询实测中，复用传输层的吞吐优势显著。** 在绕开本地虚拟网卡（TUN）、采用交叉轮询消除时序偏差、目标指向非 CDN 源站的受控基准测试中：

| 传输通路 | 中位 TTFB（6 轮交叉轮询） | 中位吞吐（2 MB 载荷，3 轮） |
|---|---|---|
| 直连 Hysteria2（UDP 443/2096/8880） | **0.62–0.82 s** | 664–690 KB/s |
| Anycast CDN 中转（8 个边缘节点） | 0.86–1.32 s | 466–856 KB/s |
| 直连 VLESS+REALITY（4 个 TCP 端口） | **1.69–2.95 s** | **236–342 KB/s** |

四个独立 TCP 端口在两项指标上同步垫底（组间差约 400 KB/s，远超单节点组内极差 125–205 KB/s），根因在于协议栈结构差异：`xtls-rprx-vision` 与多路复用（`multiplex`）互斥，每次新建并发连接都必须付出完整的长距离 TCP + TLS 握手往返开销（220 ms RTT × 3 ≈ 0.66 s）；而 CDN WebSocket 路径启用 `h2mux` 连接复用，Hysteria2 原生具备 QUIC 0-RTT/会话复用能力。

> **注**：若你的物理链路到源站具备低延迟优质直连路由，可随时在客户端 `🎯 Select` 中手动切至 `🚀 REALITY`；当服务器仅开启单一路径（未配 CDN 且关闭 Hysteria2）时，生成器会自动将 `🚀 REALITY` 放入 `⚡ Auto` 兜底。

### 关键分组参数与线上事故对照

| 参数 | 设定值 | 工程原因 |
|---|---|---|
| `interrupt_exist_connections` | **`false`** | 设为 `true` 会在每次探测切换时强制掐断正在传输的长连接；在 CDN `h2mux` 路径上更会导致复用流重拆，引发数分钟卡顿 |
| `interval` | **`5m`** | 过短（如 30 s）会在存在慢超时成员的链路上持续产生无效探测开销 |
| `tolerance` | **`80 ms`** | 长距离跨洋链路延迟标准差常达数百毫秒，缺少迟滞阈值会导致自动组在两个相近节点间高频抖动切换 |
| `connect_timeout` | **不显式截断** | 高时延弱网环境下完整握手常需 1.3–6.5 s，过低的 4–8 s 硬截断会误杀本可成功的连接 |
| Clash 组类型 | **`url-test`（禁用 `fallback`）** | `fallback` 仅按列表顺序取第一个“未超时”节点，容易将流量永久钉死在高延迟慢路径上 |

## 5. CDN WebSocket 中转：解决精确“每 2 分 05 秒断流”的空闲回收问题

启用反向代理 CDN WebSocket 路径后，最典型的线上报障是“连接正常建立，但每隔 **2m05s–2m07s** 准时中断重连”。

排查中最容易误判的三个方向均非根因：

| 常见怀疑对象 | 真实核查结论 |
|---|---|
| 源站 `nginx` `proxy_read_timeout` | 模板已设为 `3600s`，不会产生 125 秒周期 |
| 客户端 TCP Keepalive / `keep-alive-idle` | TCP Keepalive 是**逐跳（Hop-by-Hop）传输层机制**，在 CDN 边缘节点即被终结，无法穿透至应用层代理状态机 |
| 客户端自动组误切换 | 固定单节点复现依然准时在约 125 秒断开 |

**真正根因是主流 CDN 边缘对被代理 WebSocket 连接的约 100 秒无帧空闲超时（Idle Timeout）**：只要双向在约 100 秒内没有任何 WebSocket 应用层数据帧通过，边缘网关即主动关闭上游连接；而 `sing-box` 内置的 `h2mux` / `smux` / `yamux` 均不主动发送 WebSocket 控制层 Ping 帧。

本栈采用**源站数据面透明帧边界保活注入**（`scripts/ws_ping_inject.py`）根治：

```text
Anycast CDN --TLS--> nginx:8443 --WS--> ws-ping-inject:18444 --TCP--> sing-box:18443
```

在完成 HTTP `101 Switching Protocols` 握手后，`ws_ping_inject.py` 轻量解析服务端至客户端方向的 WebSocket 帧头长度，**严格在完整帧边界之间**每 25 秒注入一个空载荷 WebSocket `PING` 控制帧（Opcode `0x9`）。必须在帧边界注入 —— 若插入尚未转发完毕的大帧中部，将永久破坏字节流对齐；同时针对超过 16 MiB 的超大单帧启用零缓冲流式直通，配合 `MemoryMax=128M` 与双端 `TCP_NODELAY`，兼顾低延迟与内存确定性安全。

### CDN 中转路径的其余硬约束

- **多路复用协议必须锁定 `h2mux`**：在该链路上启用 `yamux`/`smux` 会触发客户端 `context canceled` 或周期性断流；并发连接数设为 `4` 以平衡丢包队头阻塞与边缘散列。
- **回源端口严禁复用 `443`**：`443` 由 `sing-box` 独占，且 REALITY 会将非认证流量透明转发至目标握手站；安装器严格限制回源端口为常见 HTTPS 回源白名单端口（`2053 / 2083 / 2087 / 2096 / 8443`）。
- **源站防火墙与 SNI 隐身硬化**：回源端口在 UFW 中仅向官方公布的 CDN 回源 IPv4/IPv6 网段放行，且 `nginx` 默认配置 `default_server` + `ssl_reject_handshake on`，防止全网扫描器通过未知 IP 握手套取源站域名证书。

## 6. Anycast 边缘节点优选：为何绝不能按 TCP 握手 RTT 排序

在多跳中转链路上，仅凭客户端到边缘节点的 TCP 握手延迟选路曾连续两次导出最差结果：

| 网络类型 | 全场 TCP 握手最快的边缘 IP | 实际端到端吞吐表现 |
|---|---|---|
| 移动蜂窝 CGNAT 链路 | `104.19.63.243`（握手 **61 ms**） | 端到端吞吐仅 **0.16 Mbps** |
| 固网宽带链路 | `104.20.29.23`（握手 **89.5 ms**） | 端到端吞吐 **108 KB/s（全场垫底）**，比 220 ms 组慢 3 倍 |

原因非常直观：**TCP 握手 RTT 仅测量了 `客户端 → CDN 边缘` 第一跳，完全遗漏了 `CDN 边缘 → 源站` 的跨洋回源链路质量。**

> **多跳测量公理**：在任何多跳代理或 CDN 架构中，单跳延迟只能用作“剔除不可达地址”的初筛漏斗；最终排序必须基于端到端真实载荷传输（TTFB / 吞吐）。

`scripts/pick-cf-ip.py` 严格遵循该两阶段法：
1. **初筛（Screen）**：并发 TCP 握手，快速过滤当前网络下路由不可达的边缘网段；
2. **端到端交叉轮询（Cross-Polled TTFB）**：对存活候选穿透请求源站对象，按 **成功率第一、跨 `/16` 网段分散第二** 排序，并在“单节点自身波动极差 ≥ 节点间中位数差”时主动提示噪声主导、避免盲目更换配置。

```bash
# 在待评估的客户端所在物理网络执行（通过 --interface 绑定物理网卡绕开本地虚拟网卡）
python3 scripts/pick-cf-ip.py --domain example.com --interface en0
```

## 7. 网络工程测量五原则

### 7.1 测量前必须物理绕开本机 TUN 与环境变量代理

开启虚拟网卡（TUN）时，本机对远端 IP 的 `ping` 可能显示 `0.58 ms`、`nc` 连接仅 `0.02 s` —— 这是本地栈拦截回环的假象，数据完全无效。单纯使用 `curl --interface en0` 亦可能受 Fake-IP DNS（`198.18.0.0/15`）或 `HTTP_PROXY` 环境变量干扰。

```bash
# 正确基线确认：清空环境代理 + 绑定物理网卡，确认返回的是当前物理宽带公网出口 IP
curl --noproxy '*' --interface en0 https://checkip.amazonaws.com
```

`pick-cf-ip.py --interface` 底层调用 `IP_BOUND_IF`（macOS）/ `SO_BINDTODEVICE`（Linux）直接在内核路由层绑定物理接口。

### 7.2 结合日志级别解读“无日志”

服务端默认 `log.level` 为 `warn` 时，**正常转发的连接不产生任何日志**。“过去一小时没有某入站的日志”代表**零报错**，而非“没有流量经过”。统计真实流量应查询内核态计数器：

```bash
iptables -t nat -L ANYREALITY_ALTPORT -v -n   # 查看 pkts/bytes 硬件计数
ss -nt state established | grep -c 18443
```

### 7.3 在高抖动广域网上先区分信号与噪声

长距离广域网延迟标准差可达 1 秒以上，顺序执行“先跑完 A 组 10 次、再跑 B 组 10 次”极易把分钟级背景拥塞误判为参数优劣。必须采用 `A → B → C → D` **交叉轮询（Interleaved Cross-Polling）**，且仅当**组间中位数差显著大于组内极差**时才采信调优结论。

### 7.4 坚持端到端验证，拒绝局部指标外推

见第 6 节。任何只覆盖半程链路的指标均不可作为选路依据。

### 7.5 验证进程“运行态”，而非磁盘“静态文件”

| 变更对象 | ❌ 不充分的验证 | ✅ 确定性运行态验证 |
|---|---|---|
| `nginx` 配置 | `nginx -t` 通过且 `reload` 返回 0 | `nginx -T \| grep <关键指令>`（防止软链被静态旧文件替换） |
| 内核 `sysctl` | 配置文件已写入磁盘 | `sysctl -n <key>` 校验内核实时生效值 |
| 订阅配置结构 | `sing-box check` 语法通过 | `check_profile.py` 校验全部拓扑与分流顺序不变量 |
| 规则集内联 | 缓存目录存在 JSON 文件 | 已发布订阅中 `type == "inline"` 且 `remote` 数量为 0 |

## 8. 内核参数调优：单一配置源与实时回读校验

Linux `/etc/sysctl.d/*.conf` 按字典序加载，同名键由排序靠后的文件静默覆盖。若将网络参数分散在多个 `99-*.conf` 文件中，极易出现“修改了文件但被后续文件覆盖”的静默失效。

本安装器强制收敛至唯一文件 `/etc/sysctl.d/99-anyreality.conf`，写入后立即调用 `sysctl -n` 逐项核验，并在每次运行 `scripts/check_sysctl.py` 与健康检查时执行防漂移复核：

| 内核参数 | 设定值 | 广域网传输工程依据 |
|---|---|---|
| `tcp_congestion_control` / `default_qdisc` | `bbr` / `fq` | 高时延有损广域网吞吐与排队延迟控制的基准组合 |
| `tcp_slow_start_after_idle` | `0` | 禁止长连接空闲后重置拥塞窗口，消除 200 ms 链路上突发请求的慢启动停顿 |
| `rmem_max` / `wmem_max` | `33554432` (32 MiB) | 匹配跨洋带宽时延积（BDP：200 ms × 1 Gbps ≈ 25 MB），解除默认小缓冲吞吐封顶 |
| `tcp_keepalive_time` / `_intvl` / `_probes` | `60` / `15` / `4` | 适配运营商 CGNAT 常见的 30–90 秒空闲映射回收窗口，防止长空闲连接静默僵死 |
| `tcp_retries2` | `8` | 缩短死连接重传挂起时间，加速客户端向健康路径切换 |
| `tcp_notsent_lowat` | `131072` (128 KiB) | 降低发送端套接字未发队列积压，避免大流量传输阻塞交互式小包 |
| `netdev_max_backlog` | `16384` | 为高并发 UDP/QUIC（Hysteria2）突发流量留足网卡收包队列余量 |

## 9. 本地分流与 DNS 顺序不变量

在虚拟网卡（TUN）模式下，操作系统全量流量进入路由引擎，**本地站点访问变慢几乎均源于分流或 DNS 顺序缺陷（导致本地 CDN 流量跨洋折返），而非远端网关带宽不足**。

`scripts/build_profile.py` 构建的分流栈严格遵循两项关键不变量（由 `check_profile.py` 静态门禁守护）：

1. **所有基于 IP/CIDR 的规则之前必须存在 `action: resolve`**：`sing-box` 路由引擎默认不会为评估 `geoip` 或 `ip_cidr` 规则而主动发起域名解析；缺少前置 `resolve` 会导致 IP 规则语法合法却永远无法命中域名请求。同时，仅当下游确实存在 IP 规则时才按需发射 `resolve`，避免无谓改写后续连接的目标主机名。
2. **AAAA-only 验证组件域名的 DNS 策略豁免**：`challenges.cloudflare.com` 旗下验证子域长期仅发布 IPv6 `AAAA` 记录。在全局 `ipv4_only` 策略下，必须在 **DNS 规则层**（而非路由层）为其单独声明 `prefer_ipv4`（允许回退解析 `AAAA` 并经远端节点转发），否则客户端在建立连接前即收到空解析响应，导致验证控件永久无法加载。

## 10. 生产运维六项纪律

1. **防火墙放行必须显式区分 TCP 与 UDP**：`ufw allow 443` 仅放行 TCP；Hysteria2 必须显式配置 `443/udp`，体检脚本逐协议独立核查。
2. **连接凭据锁定原则**：UUID、口令、端口、公钥与 `short_id` 一旦投产即锁定，仅在确有泄露证据或明确变更需求时使用专用轮换工具更新，杜绝无故批量重生成导致客户端断连。
3. **服务端入站与客户端订阅原子同步**：端口、SNI、口令与公钥变更必须通过 `rebuild-profiles.sh` 同步重生成并校验三态订阅产物。
4. **“构建 → 结构校验 → 内核语法校验 → 原子替换”流水线**：任一校验环节失败立即中止发布，保留线上旧版可用订阅。
5. **数据面全组件纳入巡检台账**：`sing-box`、`nginx`、`ws-ping-inject`、NAT 重定向链与定时任务均受 `healthcheck.sh` 统一覆盖。
6. **严禁手工拷贝静态订阅副本**：避免多副本长期静默漂移。
