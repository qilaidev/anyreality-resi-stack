# 国内网络优化：三条路径、为什么是这三条，以及怎么量

> 这份文档回答一个问题：**为什么一个"能连上"的节点，在国内不同线路、不同时段
> 会表现得完全不一样，以及怎么把它做成稳定可用的。**
>
> 每一条设计都对应一次真实故障或一轮真实测量。凡是"看起来合理但被实测推翻"的，
> 这里保留推翻的过程 —— 因为下一个人最可能踩的，正是那个看起来合理的版本。

---

## 0. 一句话结论

**单一路径必然会在某条线路上失效，而且失效时服务端完全看不出来。**
所以本项目默认同时开三条路径，让客户端自己去赛跑：

| 路径 | 传输 | 什么时候它是唯一能用的 | 什么时候它废了 |
|---|---|---|---|
| **REALITY** | TCP 443 + 备用口 | 电信 / 联通多数线路，直连最快 | 移动 / 广电常见：SYN 通过、ClientHello 被丢 |
| **Hysteria2** | UDP | TCP 被针对性干扰时 | 部分移动线路整段封 UDP |
| **CDN 中转** | TCP 443 → CDN → 源站 | **裸 IP 被整段黑洞时的唯一出路** | 需要域名；多一跳延迟 |

三条都不是冗余，是互补 —— 它们的失效原因互不相关。

## 1. 协议：为什么默认不是 AnyReality

本仓库曾经把 **AnyTLS + REALITY** 作为默认，论证是充分的：填充压 TLS-in-TLS 特征、
REALITY 补服务端伪装、弱网实测优于 Trojan。**结论仍然错了。**

错的地方不在推理，在于**选型时只看了服务端，没看客户端内核的覆盖面**：

> mihomo 的 `anytls` 配置块**没有 `reality-opts` 字段**，`public-key` / `short-id`
> 无处可填（[官方文档](https://wiki.metacubex.one/en/config/proxies/anytls/) ·
> [issue #2155](https://github.com/MetaCubeX/mihomo/issues/2155)）。
> 于是 Clash 系订阅里**主力节点根本写不出来**。

这个故障的形状值得记住：

- 服务端全绿，`sing-box check` 通过
- 跑 sing-box 内核的用户完全正常，一点问题都报不上来
- **只有 Clash 用户没有主力节点，而且他们看到的是"节点列表里少了几个"，不是报错**

从服务端**看不出任何异常**，所以它拖了一个月才被定位。

> **规矩**：选协议先问「我要覆盖的每个客户端内核，都能把这个节点写出来吗」，
> 再问「它快不快」。只有单一内核支持的协议，等于把另一半用户静默砍掉。

所以现在：

- **默认 `--protocol vless-reality`**（VLESS + REALITY + xtls-rprx-vision）——
  sing-box 与 mihomo 都能握手。
- `--protocol anytls-reality` 仍然保留，填充特性确实更好。**但选它就没有 Clash 订阅**，
  安装器会直接告诉你这一点，`build_profile.py` 也会拒绝生成 YAML 而不是生成一份残缺的。

### 推论：协议下线后要去搜脚本和文档

一份**自信地指向错误方向的文档，比没有文档更危险**。协议或架构变更后，
去搜所有还会部署旧架构的脚本（尤其是没挂在任何 cron/systemd 上、看起来无害的那些）
和所有还在推荐旧路线的文档。

## 2. 端口：443 是默认，但备用口不是可选项

2026 年 7 月在联通线上的实测非常干净：

| 测试 | 结果 |
|---|---|
| 裸 TCP 三次握手（22 / 80 / 443 / 2087） | ✅ 全通 |
| REALITY over TCP 2053 / 2083 / 2087 | ❌ 超时，440 次连接零成功 |
| REALITY over TCP **443** | ✅ 可用（195–242 ms） |

干扰形态是**放行 SYN、丢掉 TLS ClientHello**。结论看起来很硬：高位端口全废，只能用 443。

**五周后，同一条线，结论反转：**

| 端口 | 延迟 |
|---|---|
| 443 | 1520–3783 ms |
| 8880 | **1269 ms** |
| 40443 | **1264 ms** |

443 反而成了被拖得最慢的那个。同期广电对该 IP 整段黑洞、移动在 443 上 ClientHello 后挂死 12 秒。

> **教训不是"用高位端口"，而是"单次、单线路的测量结论会过期"。**
> 干扰是间歇的、按运营商分化的、按周变化的。任何"我们测过了，X 端口不行"
> 都有保质期。

所以现行策略：**443 作主口（兼容性最好、最不可疑），2096 / 8880 / 40443 作备用，
由客户端 urltest 自动选活的那个。**

备用端口用 **iptables NAT REDIRECT** 实现，不是新开监听：

- sing-box 配置零改动，没有第二份配置要同步
- 回退只需要清掉一条自有链，不碰 Docker 等别人的 NAT 规则
- 因为改写发生在 `nat/PREROUTING`，`filter/INPUT` 看到的已经是 443，
  **UFW 不需要为备用端口放行**
- **代价：这些端口不会出现在 `ss -tlnp` 里。这是预期行为，不是故障，别去"修"**

```bash
# 看它们是不是真的在生效（数的是内核里的规则，不是文件）
iptables -t nat -S ANYREALITY_ALTPORT
```

## 3. 客户端开机卡死：一个「必须先联网，而联网又依赖尚未就绪的代理」的环

这是本项目影响面最大的一个坑，因为**它让客户端根本起不来**，而用户的描述是
"这个 App 一点就退"。

### 链条

1. sing-box **启动时**必须把所有 `type: remote` 的 rule-set 下载完才继续，
   任何一个失败就 `FATAL` 退出
2. 下载走 `download_detour` 指定的代理组，而**冷启动时 urltest 还没有任何测速结果，
   只能取第一个成员**
3. 联通上第一个成员能通 → 1 秒拉完，一切正常
4. 移动上第一个成员是死的 → 5 秒超时 → `FATAL: initialize rule-set` →
   内核拒绝启动 → 客户端监管进程判定内核已退出 → 自动重启 → 再撞同一堵墙

"重启电脑就好了"是因为重启后时序变了、那次下载碰巧成功 —— **从来没真正修好。**

同一批规则集文件，在抖动线路上可以在几分钟内从 0.6 秒恶化到「连 8 KB 都 10 秒超时」。
首次导入订阅极易踩中，而用户完全看不出原因。

### 三道防线（缺一不可）

| 防线 | 本项目的做法 |
|---|---|
| **订阅侧** | rule-set **全部 `inline`**，启动期零网络请求。`check_profile.py` 拒绝任何 `type: remote`，`rebuild-profiles.sh` 不通过就不发布 |
| **分组顺序** | `⚡ Auto` 把**双网都通的那条（CDN）排第一**，让冷启动那次请求必定走活路 |
| **客户端本地** | 给客户端补齐它缺的 `.srs`（见下） |

内嵌的体积代价比想象中小 —— 但**前提是规则集选对了源**。在一台真机上实测：

| 规则集 | 条目 | 体积 |
|---|---:|---:|
| `geosite-cn` | 9,131 | 152 KiB |
| `geoip-cn` | 7,876 | 142 KiB |
| `geosite-category-ads-all` | 890 | 18 KiB |
| `geosite-cn-extra`（本仓库维护） | 71 | 1 KiB |

最终订阅 **0.56 MiB**，gzip 后 **81 KiB**；订阅服务会按 `Accept-Encoding` 压缩，
所以线上实际传输约 **84 KB**。原先「订阅 15 KB + 分 4 次下载 265 KB」的总量是 280 KB，
5 次请求 —— 现在是 1 次 84 KB 的请求，且**启动期一次都不发**。

> ☠️ **选错源会让这个数字变成 3.4 MB。** 另一个常用镜像的 `geosite/cn` 把每个属性变体
> 都摊平，同样的覆盖面变成 **111,305 条 / 1.7 MiB**，订阅整体 3.36 MiB。
> 规则是**内嵌**的，而订阅是手机在烂线路上反复重下的 —— 这个差别就是订阅本身。
> `fetch-rulesets.sh` 因此优先用 SagerNet 的 `.srs` 本地反编译，镜像只作兜底并会打印提示。

下载被移到服务器上，由 `refresh-rulesets.timer` 每周执行：服务器有干净的上行，
失败就保留上一份，客户端启动永远不碰网络。

```bash
# 自查：客户端日志里出现这个，说明这个环还在
grep -c "raw.githubusercontent" <你的客户端 kernel.log>
```

> ⚠️ **旧订阅也会把这个环带回来。** 客户端里若还留着已下线服务器的旧订阅，
> 它自带的 `type: remote` + `download_detour` 会重新引入死锁 —— **即使它当前没被选中。**
> 旧订阅要删干净。

## 4. 分组：为什么 `⚡ Auto` 里没有直连 REALITY

urltest 在第一次连接时没有任何测速结果，**只能用第一个成员**。所以 0 号位决定了
客户端启动后头几秒能不能用 —— 而在裸 IP 被黑洞的线路上，只有 CDN 那条会应答。

默认成员顺序：**CDN → Hysteria2**，直连 REALITY 只放在手选列表里。理由有两条：

**① 探测它会把组卡住。** 在 ClientHello 被挂死 7–12 秒的线路上，
每个探测周期都有一条成员在那儿慢慢失败。

**② 两轮独立实测里它都垫底。** 西安联通 AS4837，绕开 TUN、交叉轮询、
目标故意选非 CDN 的源：

| 通路 | TTFB 中位（6 轮） | 吞吐中位（2 MB，3 轮） |
|---|---|---|
| 直连 Hy2（443/2096/8880） | **0.62–0.82 s** | 664–690 KB/s |
| CDN 中转（8 条） | 0.86–1.32 s | 466–856 KB/s |
| 直连 VLESS+REALITY（4 个端口） | **1.69–2.95 s** | **236–342 KB/s** |

四个独立端口 × 两项指标同向垫底，不是噪声（组间差约 400 KB/s，
明显超过任一节点自身的组内极差 125–205 KB/s）。因为**四个端口一起慢**，
所以不是端口级干扰，是裸 IP 的 TCP 路径本身被压。

结构性原因也指向同一个方向：REALITY 用 `xtls-rprx-vision`，
而 **vision 与 multiplex 互斥**，每条新连接都要付满一次 TCP+TLS 握手
（该线 RTT 220 ms × 3 ≈ 0.66 s）；CDN 路径有 h2mux 复用、Hysteria2 是 QUIC 会话复用，
两者都不付这笔钱。

> ⚠️ **这不推翻「联通能打裸 IP」。** 裸 IP 443 依然可达（握手 220 ms、成功率 6/6），
> 它只是**慢**。「能连」和「快」是两件事，别拿其中一个推另一个。
>
> 如果你的线路上直连才是最快的（很多电信线是这样），把 `🚀 REALITY` 手选出来用，
> 或者改 `scripts/build_profile.py` 里的 `auto_members()`。

只有一条路径可用时（没配 CDN、关掉了 Hy2），它当然会进 `⚡ Auto` ——
上面那条规则是为了「不去探测一条会卡住的路」，不是「这条路不能用」。

### 其他几个分组参数，每个都对应一次事故

| 参数 | 值 | 为什么 |
|---|---|---|
| `interrupt_exist_connections` | **false** | true 会让每个探测周期掐掉正在承载流量的隧道；在 CDN 路径上还会重新拆 mux，卡好几分钟 |
| `interval` | **5m** | 30 s 时，一条要挂 7–12 秒才失败的成员会让通道长期忙于失败 |
| `tolerance` | **80 ms** | 没有滞回，两个边缘之间的纯噪声差（跨境链路标准差可达 1.05 s）会让组来回抖 |
| `connect_timeout` | **不设** | 实测国内握手 1.3–6.5 s、CDN 通道 TTFB 常在 1–4 s。4–8 s 的上限会把本来能连上的连接掐掉 |
| Clash 组类型 | **url-test，绝不用 fallback** | fallback 只取第一个「活的」＝永远选最慢的那条（同一客户端实测 11.12 s vs 1.20 s） |

## 5. CDN 中转：能连上，然后每 2 分 05 秒断一次

配好 CDN 路径后最常见的报障是「连上了，但过一会儿就断」，而且断得**精确到秒**：
2m05s / 2m06s / 2m07s，反复如此。

排查时最容易怀疑的三个方向**全是错的**：

| 怀疑对象 | 实际 |
|---|---|
| nginx `proxy_read_timeout` | 已经是 3600 s，不可能是 125 s |
| 客户端 TCP keepalive / `keep-alive-idle` | TCP keepalive 是**逐跳**的，在 CDN 边缘就终止了，CDN 根本看不见 |
| 「自动组选错了节点」 | 换哪个节点都一样，因为根因不在节点 |

真凶是 **CDN 对被代理 WebSocket 的空闲超时（普通套餐约 100 秒）**：
双向都没有帧就关闭。保活必须靠**应用层 ping**，也就是真的变成 WebSocket 帧的那种。
而 sing-box 的 h2mux / smux / yamux 都不发 WS ping。

解法是在源站侧注入：

```
CDN --TLS--> nginx:8443 --WS--> ws-ping-inject:18444 --TCP--> sing-box:18443
```

`ws_ping_inject.py` 在 HTTP 101 之后，把服务端到客户端方向按 WebSocket 帧解析，
**在帧边界上**每 25 秒注入一个空 ping 帧（opcode 0x9）。必须在帧边界注入 ——
写进一个只转发了一半的帧里会让流永久错位，而表现出来的症状和空闲超时一模一样，
让修复和 bug 无法区分。

> 源站侧的 ping **不需要刷新订阅就对所有 CDN 客户端生效** —— 它在数据路径上，不在配置里。

### CDN 路径的其他硬约束

- **mux 必须是 `h2mux`。** 在这条 VLESS+WS+CDN 上，sing-box 客户端用 yamux/smux
  会立刻 `context canceled` 握手失败；mihomo 开 smux 约每 5 分钟掉一次。
- **mux 并发保持 4。** 只用 2 条 TCP 在丢包链路上会队头阻塞；开太多则把 mux
  摊到多个边缘上。
- **源站端口不能是 443。** sing-box 占着 443，而 REALITY 会把所有非代理流量
  **原样转发给 handshake 目标**，nginx 永远看不到这些连接。CDN 支持 HTTPS 回源的端口
  只有 443 / 2053 / 2083 / 2087 / 2096 / 8443，安装器只接受这几个 —— 选错的表现是
  「在服务器上本地测正常，走 CDN 就 522」，很像源站故障。
- **回源端口只对 CDN 网段放行**，且网段列表是**抓取**的，不是凭记忆写的
  （见第 7 节）。

## 6. 优选 IP：两次都栽在「按握手 RTT 选」

选 CDN 边缘 IP 这件事，在两条不同线路上用同一个错误方法栽了两次：

| 线路 | 全场握手最快的 IP | 它的端到端表现 |
|---|---|---|
| 移动 | `104.19.63.243` 握手 **61 ms** | 吞吐 **0.16 Mbps** |
| 联通 | `104.20.29.23` 握手 **89.5 ms**（比其他快 2.4 倍） | **108 KB/s，全场倒数第一**，比 220 ms 那批慢 3 倍 |

原因很简单：**握手 RTT 只量了「客户端 → 边缘」，而源站在另一端 ——
漏掉了「边缘 → 源站」那一整段。**

> **凡是多跳链路，只测其中一跳的指标都可能指向反方向。**
> 单段指标只能用来初筛（把根本连不上的扔掉），排名必须端到端。

`scripts/pick-cf-ip.py` 就是按这个做的：握手只用来筛掉不可达的（某条联通线上
329 个采样只有 51 个能完成握手 —— 封锁面 85%），排名一律端到端跑真流量、交叉轮询。

### 选取标准：成功率优先，其次网段分散，**不按快慢**

同一档成功率里的吞吐排名往往是噪声：实测 5/5 那一档中位吞吐 284–309 KB/s，
而**单个节点自己的波动就有 295–318** —— 组内极差 ≥ 组间差，这个排序没有意义。
`pick-cf-ip.py` 会自己算这两个量并在噪声主导时明确告诉你「别按这个排名改」。

### 删 IP 之前先想清楚一件事

**边缘归属是按线路走的，不是 IP 的属性。** 同一个 `104.17.48.94`
在移动线落香港（握手 60 ms），在西安联通落美国（219 ms）。
在你这条线上废了，不等于在别人那条线上废了。

```bash
# 在你要优化的那条线上跑，不是在服务器上跑
python3 scripts/pick-cf-ip.py --domain example.com --interface en0
```

## 7. 怎么量：五条方法论

这一节不讲某个具体故障，讲**怎么量、以及怎么判断量出来的东西可不可信**。
每一条都真栽过。

### 7.1 测之前，先绕开你自己的 TUN

**症状**：`ping` 洛杉矶服务器显示 **0.589 ms**，`nc` 连 443 只要 0.02 s。
看着像本地机房 —— 其实是本机 TUN 把包截走后在本机绕了一圈。
**这类数据全部作废，而且会把你引向完全相反的结论。**

`curl --interface en0` **也不够**：

- 域名解析仍走 TUN，会拿到 fake-ip（198.18.x.x），表现为瞬间失败（exit 7）而不是报错
- 本机 `HTTP_PROXY=127.0.0.1:7890` 会把 https 塞进一个**可能根本没在监听**的端口，
  同样是秒失败，很像"线路不通"
- `nc -s <本机IP>` **无效** —— 只绑源 IP、不改路由，照样走 TUN，会骗你说"通"

```bash
# 正确姿势：绕环境代理 + 强制物理网卡，然后确认出口 IP 是运营商的
curl --noproxy '*' --interface en0 http://ip.3322.net
```

`pick-cf-ip.py --interface` 用的是 `IP_BOUND_IF`（macOS）/ `SO_BINDTODEVICE`（Linux），
真正改路由，不只是绑源地址。

**ICMP 也一样会被截。** 某次 `ping` 显示 1.5 ms，真实 TCP 握手是 220 ms。

### 7.2 日志级别决定「没有日志」怎么读

服务端 `log.level` 是 `warn` 时，**成功连接根本不写日志**。

曾经的真实误判：看到「近 1 小时日志里没有 Hy2」，据此断定「手机没走 Hy2」。
实际含义是「**Hy2 没有报错**」—— 方向正好相反。

```bash
jq -r .log.level /etc/sing-box/conf/00_log.json   # 先确认级别，再解读计数
```

要看**使用量**而不是**错误量**，用内核计数器，不要用日志：

```bash
iptables -t nat -L ANYREALITY_ALTPORT -v -n   # pkts/bytes 是真实流量
ss -nt state established | grep -c 18443
```

### 7.3 抖动大的链路上，先证明差异不是噪声

跨境移动链路的标准差可以到 1.05 秒。**在这种链路上，单次 A/B 几乎一定会骗你。**

方法：**交叉轮询**（A→B→C→D 循环若干轮，而不是跑完 A 再跑 B），
然后比较**组内极差**与**组间中位数差**：

| 实例 | 组内极差 | 组间中位数差 | 判定 |
|---|---|---|---|
| mux 参数 A/B | **10.47 Mbps** | 7.85 Mbps | ❌ 组内 > 组间，**无效**，维持原状 |
| 香港 vs 洛杉矶边缘 | 0.09–0.46 s | 0.39 s | ✅ 差异远超噪声，可据此改 |

那轮 mux 测试第一次测出「D 变体吞吐是现行的 6 倍」，差点就改了。
重测三轮后发现同一配置自己的波动比配置之间的差异还大 ——
**按它改属于拿噪声当信号。**

### 7.4 端到端测，不要只测一段

见第 6 节。同一个错误在两条线路上重复了两次，代价是两次改错了优选 IP。

### 7.5 验「运行态」，不要验「文件」

本项目已经在三个地方栽在同一个模式上：

| 改的东西 | ❌ 不足以证明生效 | ✅ 正确的验证方式 |
|---|---|---|
| nginx 配置 | `nginx -t` 通过、`reload` 成功 | `nginx -T \| grep <关键字>` |
| sysctl | 文件里写了 | `sysctl -n <key>` |
| 订阅结构 | `sing-box check` 通过 | 真起一个实例 + `check_profile.py` |
| 规则集 | 文件存在 | 订阅里 `type` 必须是 `inline`，remote 数为 0 |
| 协议下线 | 服务端配置改了 | `grep -c <旧协议> <配置>` 为 0，**且**搜遍所有部署脚本与文档 |
| 优选 IP | 握手 RTT 快 | 端到端跑一遍 |

`nginx -t` 只说明磁盘上的文件语法正确 —— 在 `sites-enabled` 软链被换成一份
过期的普通文件之后，它依然通过。`nginx -T` 打印的才是进程**真正持有**的配置。

### 7.6 排查顺序清单

```
1. 我现在在哪个网络？       curl --noproxy '*' --interface en0 http://ip.3322.net
2. 我的测量绕开 TUN 了吗？   出口 IP 必须是运营商的
3. 日志级别是什么？          决定「没有日志」怎么解读
4. 服务端收到包了吗？        nat 计数器 / conntrack，不是日志
5. 是哪一跳慢？              分段测：TCP → TLS → TTFB → 端到端
6. 这个差异是噪声吗？        交叉轮询，组内极差 vs 组间差
7. 改完验运行态了吗？        见 7.5 的表
```

## 8. 内核参数：只有一个文件，而且只验生效值

`/etc/sysctl.d/` **按文件名排序加载，后者静默覆盖前者**。本项目审计过的一台机器上
有 5 个 `99-*.conf`、14 个键被重复定义，其中包括
`net.ipv4.tcp_congestion_control` 同时出现在两个文件里。

于是「改了 `99-bbr.conf` 却毫无效果」是**必然**，而且改的人看不出任何异常。
这和 nginx `sites-enabled` 软链被换成普通文件是**同一类坑：改动看似生效，实际没有。**

所以安装器现在：

- 只写 **一个** `/etc/sysctl.d/99-anyreality.conf`，并删掉自己以前写的
  `99-bbr.conf` / `99-swap-tuning.conf`
- 写完立刻用 `sysctl -n` **验最终值**，不一致就告警
- `scripts/check_sysctl.py` 在每次体检时复验，漂移即报

调的是什么、为什么：

| 参数 | 值 | 理由 |
|---|---|---|
| `tcp_congestion_control` / `default_qdisc` | bbr / fq | 跨境有损链路上的基本盘 |
| `tcp_slow_start_after_idle` | 0 | 长连接空闲后不重置拥塞窗口；否则每次突发都从慢启动重来，在 200 ms 链路上非常明显 |
| `rmem_max` / `wmem_max` | 32 MB | 跨境 BDP：200 ms × 1 Gbps ≈ 25 MB。默认缓冲会在链路之前先把吞吐卡死 |
| `tcp_keepalive_time` / `_intvl` / `_probes` | 60 / 15 / 4 | 国内 CGNAT 30–90 s 回收空闲 TCP 映射。慢于它，空闲隧道回来就是死的 |
| `tcp_retries2` | 8 | 默认约 15 分钟才放弃一个死连接，在丢包链路上会长期占着客户端的槽位 |
| `tcp_notsent_lowat` | 128 KB | 别让交互流量堵在已经排进内核的大文件后面 |
| `netdev_max_backlog` | 16384 | Hysteria2 是 UDP：队列不够时内核丢包，看起来像"线路差" |

> **要加参数就加在这个文件里**，改完 `sysctl -n <key>` 确认，
> **不要再新建 `99-*` 文件** —— 那会把上面那个坑重新挖出来。

## 9. 国内直连：为什么慢的是"分流"，不是"节点"

最常见的一类报障是「导入订阅后，连淘宝、微信、B 站、网银都变慢了」。
这几乎从来不是节点的问题：

**TUN 模式下没有"全局 / 直连"开关，流量走不走代理完全由规则决定。**
规则不完善就会把国内流量也发去海外 —— 国内站走洛杉矶叫「慢」，
不是节点带宽不够。

本项目下发的配置有四层，外加两条容易被忽略的细节：

1. 内网直连
2. 广告拦截
3. **国内直连**：内联安全网（约 60 条高频域名，不依赖任何下载）→
   `geosite-cn-extra`（本仓库维护的国内 CDN 扩充名单）→ `geosite-cn`
4. 兜底走节点

**细节一：IP 规则前面必须有 `action: resolve`。**
客户端发来的是域名，sing-box 不会为了评估一条 IP 规则而主动去解析它 ——
`route.default_domain_resolver` 也不改变这一点，它只决定"有人问的时候用哪个解析器"。
没有 resolve，`geoip-cn` 这条规则**存在、合法、且永远不会命中**。
`check_profile.py` 专门守这个顺序。

反过来也要注意：`resolve` 会把后续所有连接的目标域名换成地址，
所以生成器**只在下游真的有 IP 规则时才发它**，不"以防万一"加上。

**细节二：Cloudflare 人机验证控件是 AAAA-only。**
`brunhild.challenges.cloudflare.com` 长期只有 AAAA 记录。在全局 `ipv4_only`
策略下它解析不到任何地址，验证页会永远转圈。

这个修复**必须在 DNS 层**：TUN 模式下应用在开 socket 之前就已经解析完了，
路由规则根本没机会插话 —— 查询已经返回空了。所以配置里有一条针对
`challenges.cloudflare.com` 的 DNS 例外（`prefer_ipv4`），
`check_profile.py` 会检查它还在。

## 10. 维护这套东西时的几条规矩

**① 加入站端口必须同步放行，UDP 要写 `/udp`。**
`ufw allow 443` 只开 TCP。Hysteria2 在 TCP-only 规则后面会正常监听、
从每个客户端都不可达，而服务端毫无异常。安装器和体检脚本现在都显式检查协议。

**② 连接参数是配置完就锁定的，不是需要"定期轮换"的。**
uuid、密码、端口、密钥、token、public_key、short_id —— 除非
①实测确认遇到性能瓶颈 ②有证据表明链接被泄露 ③用户明确要求，
否则不要以"顺手优化""安全最佳实践""统一规范"为由改动。
多次轮换操作实际并未解决任何问题，反而造成客户端大面积断连和反复排查。

**③ 服务端与订阅必须同步改。**
`password` / `listen_port` / `server_name(SNI)` / `short_id` 是服务端入站与
客户端订阅必须一致的四元组。只改一边 = 客户端立刻连不上，且报错极具误导性。

**④ 改线上配置必须"验证 → 生效 → 失败回滚"。**
`sing-box check` 查不出运行时错误：出现过 `check` 通过但启动 FATAL 的情况
（某个 `detour` 指向了空出站）。`rebuild-profiles.sh` 因此先构建到临时目录、
跑结构校验、再跑 `sing-box check`，全过才发布；任一步失败就保留上一份可用的。

**⑤ 数据路径上的每个进程都必须出现在清单和体检里。**
`ws-ping-inject` 曾经在 CDN 数据路径上跑了很久却不在任何清单里 ——
排查故障时完全看不见它，因为没有人会去看一个自己不知道存在的组件。

**⑥ 静态兜底必须是软链，不能是副本。**
一份手工拷贝的兜底订阅曾经无声漂移了一个多月，等它真的启用时，
客户端「成功更新订阅」然后完全连不上 —— 比没有兜底更糟，因为它看起来是成功的。
